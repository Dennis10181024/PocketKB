# PocketKB 情境演練｜組員代報與操作手冊

11 月 9 日（一）教授討論用｜約 3–4 分鐘

## 會前準備

解壓縮後，用 Chrome 或 Edge 開啟同一資料夾的 `PocketKB_教授展示.html`。整場可用教室電腦離線展示，右上角「架構與進度」是代報時的投影頁。若有 Android 手機且已安裝展示 APK，可補看六個劇本入口，現場維持離線模式。

## 建議先展示堰塞湖

| 操作順序 | 畫面重點 |
| --- | --- |
| ① 點「到河邊或橋上觀看」 | 顯示**危急失敗**，本次演練鎖定。 |
| ② 點「重新開始」，再點「繼續收拾非必要物品」 | 東側撤離路線中斷，原撤離選項消失。 |
| 接著依序點「前往公告的就近垂直避難點」、「回報目前位置與受困人數」、「留在避難點並控制物資與電量」 | 顯示**穩定待救・尚未獲救**，並回顧行動和環境變化。避難點是劇本中由公告指定的地點。 |
| ③ 再開一輪，點「確認官方撤離命令與指定路線」，再點「立即沿東側指定路線撤往高地」 | 顯示**完成撤離**。同一個起點，決策不同，結果就不同。 |

時間有限時，優先展示第 ② 條。教授想試文字輸入時，在新的一輪輸入「我可以到河邊觀看嗎？」會被當作提問，情境不會推進。

## 代報稿

> 我代報情境演練的進度。目前做了六個新版劇本，分別是宿舍火災、學校地震、住家地震受困、低窪住宅淹水、山區道路土石流和堰塞湖下游。使用者可以看現場線索、選擇行動或用文字回答，結束後會看到決策和後果的回顧。
>
> 今天用堰塞湖示範。同一個警報下，立即依指示撤離可以抵達高地，拖延會讓原路線中斷，接下來要改成避難與待救。到河邊觀看則會失敗。這個劇本要練的是現場條件改變後，如何調整決策。
>
> 原計畫書連平時的情境演練都規劃在手機端全離線。手機先用向量 RAG 找到知識和劇本，再由量化語言模型生成對話、判讀回答和推進情境。雲端模型是原計畫比較生成品質的基準。
>
> 我們目前先用獨立的劇本規則與狀態機處理行動後果。這讓同一個決策可以重現、逐條測試，也能清楚區分待救和撤離。手機端模型與向量 RAG 尚待整合。GPT API 串接有初步進度，仍待實際對話驗收。
>
> 教育設計沿用原計畫引用的防洪遊戲研究，把決策、後果和反思放在同一輪演練裡。架構上，補充參考 SayCan 將語言建議與行動可行性分開評估的做法，作為分工的類比。想請教授確認的是，後續整合端上模型時，是否保留狀態機掌管安全條件與結局。

## 教授追問時

- **目前完成什麼？** 六個新版劇本已能在 Android 離線執行，包含一個火災 v2 與五個通用 v3 劇本。新版有自由輸入、引導行動、分次完成、撤離與待救分支、失敗鎖定、回顧及本機紀錄。宿舍火災也有詢問模式與分層提示。網頁展示用堰塞湖一個劇本呈現三個結局。
- **已測到什麼？** 展示網頁在 Chrome 離線跑通三種結局與重開。Android APK 已在 API 35 模擬器安裝啟動，26 個單元測試與 5 個 Compose 介面測試通過。另有 28 個 Node／Web 測試項目通過。
- **離計畫書還有多遠？** 原訂的端上模型與向量檢索尚待整合，也還沒完成真機驗收、劇本逐條專業審查、原訂 30–45 分鐘的研究介入與前後測。現階段可以報告功能及測試結果，教育成效要等研究驗證。其他地點仍有規劃待實作，一般離線網頁也尚未接入全部新版劇本。

| 已做劇本 | 可用來說明的設計 |
| --- | --- |
| 宿舍火災 | 濃煙阻路時分次完成關門、模擬求救、位置回報與保持通訊。 |
| 學校地震 | 先掩護，等搖晃停止再依指示疏散、點名。 |
| 住家地震受困 | 沒有安全出口時，避免二次傷害、傳送位置並保存電量與體力。 |
| 低窪住宅淹水 | 撤離窗口關閉後，依劇本條件改為垂直避難與待救。 |
| 山區道路土石流 | 根據警戒及道路封閉資訊折返，改走公告路線。 |
| 堰塞湖下游 | 同一警報下可撤離、因拖延而待救，或因進入警戒區而失敗。 |

計畫書位置｜第 3 頁 RQ1 為雲端品質比較，第 5–7 頁為全離線設計，第 8 頁為離線 RAG 介入。
